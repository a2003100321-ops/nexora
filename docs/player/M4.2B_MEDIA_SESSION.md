# M4.2b MediaSession Background Playback

## Scope

M4.2b adds Android system media integration on top of the existing `player:media3`
engine. It does not add a playback screen, subtitles, danmaku, casting, DRM, VLC,
automatic source switching, or retry policy.

The playback ownership chain remains:

```text
UI
  ↓
PlayerController
  ↓
player:runtime
  ↓
PlayerEngine
  ↓
player:media3 / Media3Engine
  ↓
MediaSessionService + Media3 / ExoPlayer
```

Feature modules and `player:api` still do not expose `ExoPlayer`, `MediaItem`, or
other Media3 implementation types.

## Implemented Modules and Classes

### `player:api`

- Added `PlaybackMediaIdentity.posterUrl`.
  - This is optional and is reserved for notification artwork.
  - It does not require the UI or data-source layer to provide artwork yet.

### `player:media3`

- `NexoraMediaSessionService`
  - Android `MediaSessionService` entry point.
  - Owns the `MediaSession` lifecycle.
  - Releases the session and shared player resources when the service is
    destroyed.

- `Media3SessionPlayerOwner`
  - Internal owner for the service-backed ExoPlayer adapter and MediaSession.
  - Starts/stops the media service from inside `player:media3`.
  - Keeps ExoPlayer hidden from app, feature, runtime, and API layers.

- `ServiceBackedMedia3PlayerAdapter`
  - Keeps the `Media3Engine` API unchanged.
  - Delegates real playback commands to the service-backed Media3 adapter.
  - Stops the service when the engine is released.

- `ExoPlayerMedia3PlayerAdapter`
  - Still adapts ExoPlayer to Nexora's internal `Media3PlayerAdapter`.
  - Can now be constructed with a service-owned player.

- `Media3MediaItemMapper`
  - Continues mapping `PlaybackSessionRequest` to Media3 `MediaItem`.
  - Adds Media3 metadata for notification title and optional artwork.

- `MediaSessionLifecycleCoordinator`
  - Pure Kotlin lifecycle model used by tests.
  - Tracks foreground/background state, service destruction, service recreation,
    and playback snapshot recovery.

- `MediaSessionTransportRouter`
  - Pure Kotlin routing model for system/media transport commands:
    play, pause, seek, stop, previous, next.

### `app-mobile`

- Adds an app composition dependency on `player:media3` so the
  `MediaSessionService` manifest is merged into the mobile APK.
- No playback UI was added.

## Android Manifest and Security

`player:media3` declares:

- `FOREGROUND_SERVICE`
- `FOREGROUND_SERVICE_MEDIA_PLAYBACK`
- `POST_NOTIFICATIONS`
- `NexoraMediaSessionService`

The service is:

- `android:exported="false"`
- `android:foregroundServiceType="mediaPlayback"`
- not declared with an intent filter

This keeps the service available to the app while avoiding unnecessary exported
surface area.

## MediaSession Capabilities

The MediaSession is backed by the same ExoPlayer instance used by the Media3
engine. Android system controls can target the active MediaSession for:

- play
- pause
- seek
- stop
- previous
- next

Notification metadata is supplied through the MediaItem metadata:

- title: `PlaybackSessionRequest.media.title`
- artwork: `PlaybackSessionRequest.media.posterUrl`, when provided

## Bluetooth and Media Button Handling

Android routes headset, Bluetooth, and system media-button commands to the active
MediaSession. M4.2b verifies Nexora's command mapping with a JVM transport-router
test. Real-device Bluetooth validation remains a manual device check because it
requires OS media-button dispatch and hardware or emulator input events.

## Lifecycle Behavior

M4.2b models and tests these lifecycle rules:

- App enters background:
  - playback snapshot remains available
  - service remains active

- App resumes:
  - playback snapshot is preserved
  - UI can reattach through the existing controller path later

- Service is destroyed:
  - active playback snapshot marks restore as pending

- Service is recreated:
  - last known snapshot is returned for recovery
  - restore-pending flag is cleared

Activity does not own playback state.

## Android 12+ and Android 14 Notes

- Android 12+ restricts starting services from the background.
  Nexora starts the media service through an explicit app-owned service intent
  and catches service-start failures so playback setup does not crash the app.

- Android 14 requires a matching foreground service type and permission for media
  playback foreground services.
  Nexora declares `android:foregroundServiceType="mediaPlayback"` and
  `FOREGROUND_SERVICE_MEDIA_PLAYBACK`.

- Notification display on Android 13+ may require user notification permission.
  M4.2b declares `POST_NOTIFICATIONS`; permission request UX is intentionally not
  implemented because this phase does not build playback UI.

## Tests Added

New tests:

- `MediaSessionLifecycleCoordinatorTest`
  - app entering background keeps playback snapshot
  - app resume keeps playback snapshot
  - service destroyed marks restore pending
  - service recreated returns snapshot for recovery

- `MediaSessionTransportRouterTest`
  - routes play, pause, seek, stop, previous, next
  - clamps negative seek positions to zero

Existing Media3 contract tests continue to cover:

- FakeEngine and Media3Engine shared contract
- MP4 prepare
- HLS prepare
- DASH prepare
- error mapping
- release lifecycle
- secure URL/header policy
- cookie and credential provider injection

## Current Limitations

- No playback UI.
- No subtitle rendering.
- No danmaku.
- No casting.
- No DRM.
- No VLC fallback.
- No automatic source switching.
- No automatic retry.
- No notification permission request UX yet.
- Bluetooth/media-button behavior still needs real-device manual verification in
  a later QA pass.

## Dependency Changes

Added:

- `androidx.media3:media3-session`

Version Catalog was updated with:

- `androidx-media3-session`

The Media3 version remains aligned to the existing `media3 = 1.10.1` catalog
entry.

## Result

M4.2b establishes the Android system media foundation for background playback
without introducing a playback page or leaking Media3 implementation types across
Nexora's player architecture boundary.
